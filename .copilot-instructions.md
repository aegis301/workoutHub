# WorkoutHub Project Guidelines

## Code Style & Standards

### Python Code

- Follow PEP 8 style guidelines
- Use type hints for all function parameters and return values
- Use Google-style docstrings with Args, Returns, and Raises sections
- Maximum line length: 88 characters (Black formatter)

### FastAPI Endpoints

- Always include comprehensive docstrings with examples
- Use proper HTTP status codes and FastAPI HTTPException
- Include `summary` and `description` in router decorators
- Return MessagePack format with proper datetime serialization
- Add response schema definitions for 404 and 422 errors

### Database Models

- Use SQLModel for all database models
- Include comprehensive docstrings with field descriptions
- Add validation constraints using Pydantic validators
- Use meaningful relationship names

### Error Handling

- Use HTTPException instead of direct Response errors
- Provide clear, user-friendly error messages
- Include proper HTTP status codes (404, 422, 500)
- Log errors using the project's Logger class

## Project-Specific Patterns

### MessagePack Serialization

- Always handle datetime objects by converting to ISO strings
- Use the `serialize_for_msgpack()` utility function in sets.py
- Return `Response(content=packed_data, media_type="application/msgpack")`

### Database Sessions

- Use `Session = Depends(get_session)` for dependency injection
- Handle database errors gracefully
- Use proper SQLModel select statements

### Logging

- Import and use the project's Logger: `from ..logger.logger import Logger`
- Log important operations and errors
- Use structured logging with context

## File Organization

### Router Files

- Include module docstring explaining purpose
- Group related endpoints together
- Use consistent parameter naming
- Include comprehensive function documentation

### Model Files

- Document all fields and relationships
- Use proper foreign key constraints
- Include validation rules

## Documentation Requirements

### API Documentation

- Every endpoint must have clear summary and description
- Include example request/response where helpful
- Document all parameters and their constraints
- Explain the purpose and use case

### Code Documentation

- All functions need docstrings with Args, Returns, Raises
- Complex logic should have inline comments
- Module docstrings for all Python files

## Common Patterns to Follow

### Standard Router Structure

```python
"""
[Module] management endpoints.

This module provides REST API endpoints for managing [entity description].
"""

import msgpack
from fastapi import APIRouter, Depends, Response, HTTPException
from sqlmodel import Session, select
from ..models.models import [Model]
from ..database import get_session

router = APIRouter(
    prefix="/[route]",
    tags=["[tag]"],
    responses={
        404: {"description": "[Entity] not found"},
        422: {"description": "Validation error"},
    },
)
```

```python
    [Detailed description of what this endpoint does]
    
    Args:
        db: Database session dependency
        
    Returns:
        Response: MessagePack-encoded list of [entity] objects
        
    Raises:
        500: Database connection error
    """
    # Implementation
```

## Avoid These Patterns

- ❌ Direct Response with status codes instead of HTTPException
- ❌ Missing type hints on function parameters/returns
- ❌ Returning raw datetime objects in MessagePack responses
- ❌ Missing docstrings on public functions
- ❌ Unused imports
- ❌ Inconsistent error handling patterns

## When Making Changes

1. **Always check existing patterns** in the codebase first
2. **Follow the established documentation style** from other routers
3. **Use the project's utility functions** (like `serialize_for_msgpack`)
4. **Test the API endpoint** via the /docs interface
5. **Ensure error cases are handled** properly
6. **Run tests** to verify functionality
7. **Update documentation** if the endpoint behavior changes or new functionality is added.
8. **Update the README.md** with any new features or changes to existing endpoints.
9. **Review the changelog** and add an entry for significant changes.
10. **Update the `.copilot-instructions.md`** if new patterns or standards are established.
11. **Update the API.md** with any new endpoints or changes to existing ones.
12. **Update the DEVELOPMENT.md** with any new development practices or tools introduced.
